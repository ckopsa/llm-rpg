## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/SYNC_CONCEPTS.md for details and anti-patterns.

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.

## Architecture Overview

A 2D RPG engine designed for LLMs to build and play. **Everything is data**: a game is one JSON document (see `games/demo/game.json`), validated by zod schemas with actionable error messages, simulated deterministically, and rendered two ways from the same engine.

- `packages/engine` — pure TypeScript, no I/O; all randomness through the seeded serializable `Rng`:
  - `schema.ts` — `GameSchema`: `meta`, OPTIONAL `catalog` (absent = narrative game: validation errors, naming the fix, on wild tiles, encounter zones, trainer blocks, `give_species`/`give_item`/`sell`, and non-empty starting party/inventory; battles never engage), shared `legend`, `maps` (rows/entities/portals/encounters), `player` (`party` up to 6 `{ speciesId, level }`, `money`, `inventory` `[{ itemId, qty }]`, optional `respawn { map, x, y }` for defeat). Interaction gates: `requiresFlag` and `forbidsFlag` (skipped when the flag IS set — one-time gifts, starter pedestals) ANDed with the unified optional `when` condition object — `{flag}` / `{notFlag}` / `{var, op: eq|ne|lt|lte|gt|gte, value}` / `{all}` / `{any}` / `{not}`, evaluated by the exported `evalWhen(ctx, when)` over `{ flags, vars, money }` (missing vars read as 0 against numbers, "" against strings; `"money"` is a built-in readable var). Commands (each takes an optional `when`; false = silently skipped): `say`, `set_flag`, `set_var` (number or string), `add_var` (numeric; missing var starts at 0; add on a text var is a validation error where statically knowable, else a runtime event), `passage` (`{ title?, lines[] (min 1), citation?, when? }` — long-form text), `choice` (`{ prompt, options: [{ label, when?, commands (min 1) }] (min 1), when? }` — dialogue choice, overworld-only: a validation ERROR inside trainer `rewardCommands`; presenting one SUSPENDS the remaining commands of the current list — they resume after the chosen option's commands complete (nested choices stack continuations); options whose `when` fails are hidden, and a choice with zero open options emits an explanatory event and is skipped — validation WARNS when every option is `when`-gated), `win`, `give_species`, `give_item`, `give_money`, `heal_party` (gentle no-op event in catalog-free games), `sell` (spatial shop counter: player buys 1x `itemId` for `price`, shortfall named on failure). Entities may carry a `trainer` block: `party` (1..6 `{ speciesId, level }`), `defeatFlag`, optional `lineOfSight { dir, range >= 1 }`, `rewardMoney`, `rewardCommands`, `intro`/`defeatText`/`outro`. `validateGame` cross-checks encounter tables, command refs (interactions AND rewardCommands), trainer parties, and party members against the catalog; it WARNS (not errors) on vars/flags that are read but never written (trainer `defeatFlag`s count as flag writes; writes inside choice options count, recursively) and errors on writing the built-in `money` var; all command cross-checks recurse into choice options with full paths (`...commands[1].options[2].commands[0]`). Narrative commands (djt.3–5, each with optional `when`): `move_entity { entityId, path: Direction[], quiet? }` (`quiet` suppresses the text events but still emits the renderer cue — for ambient motion, which would otherwise narrate every drifting animal into the log), `spawn_entity { mapId?, entity }` (full EntitySchema payload; id collisions with placed entities are validation errors), `remove_entity { entityId }`, `set_tile { mapId?, x, y, char }` (char must be in the legend), `wait { beats >= 1 }`, `camera_focus { entityId } | { mapId?, x, y } | { release: true }` (exactly one target, checked), `play_music { track }`, `screen_effect { shake | flash | fade }`, `end { id, text }` (ungated `end` must be last, like `win`; `win` = sugar for `end {id:"victory"}`; `validateGame` returns all ending ids as `endings`), `teleport_player { mapId, x, y }` (destination statically checked), `show_title { text, subtitle? }`, `set_variant { entityId, variantId } | { entityId, clear: true }`. Maps take `triggers: [{ id, on: "enter" | "step" | "turn", tiles? (required for step, invalid otherwise), once (default true), when?, commands }]` — ids unique per map, step tiles bounds-checked, commands fully recursed. Entities take `sprite?` and `variants?: [{ id, when?, glyph?, sprite?, name? }]` (unique ids per entity); entity references in commands (move/remove/camera/set_variant) resolve against placed entities AND spawn_entity payloads.
  - `catalog.ts` — type chart, moves, species (learnset, `evolvesTo`, `catchRate`, `xpYield`) and items (`kind: "heal" | "capture"`; heal requires `amount`, capture requires `ballMod`, optional `price`); `statsAtLevel`, `movesKnownAtLevel`.
  - `battle.ts` — deterministic turn-based `Battle` (actions: move/switch/item/catch/run; outcomes: player_won/enemy_won/fled/captured). XP on enemy faint = `floor(xpYield * enemyLevel / 5)`; total XP for level L = `L^3`; level-ups recompute stats (heal by the HP gain) and learn learnset moves, replacing the oldest of 4. Catch p = `clamp(catchRate * ballMod * (1.3 - hp/maxHp), 0.05, 0.95)`.
  - `sim.ts` — overworld `Sim`; stepping onto a wild tile immediately starts a wild battle sharing the sim's Rng (`state.battle` non-null). In battle only battle actions are accepted: `move1..move4` (`m1..m4`), `switch1..switch6` (`s1..s6`), `item1..item9`, `catch` (alias `snare`), `run`. Battle end flows back: evolution checks at battle end; captures join the party (max 6, else gently released); defeat heals the party, halves money, respawns at `player.respawn` (default start). Empty or all-fainted party blocks wild tiles. Trainer battles (mode `"trainer"`: no run, no catch, capture items not consumed) start by interacting with an undefeated trainer or automatically via line-of-sight after any move (straight along `dir` within `range`, blocked by non-walkable tiles or blocking entities); `state.battleTrainer` tracks the trainer; victory sets `defeatFlag`, pays `rewardMoney`, runs `rewardCommands`, says `defeatText`, and afterwards the trainer chats via `interactions` (or `outro` as fallback). Trainers don't engage a player with no battle-ready kindred. `SimState` also carries `vars` (`Record<string, number | string>`, written by `set_var`/`add_var`, read by `when`), `lastPassages` (`{ title?, lines, citation? }[]` from `passage` commands — cleared at the start of every `act()`, exactly like `lastEvents`; each passage is also pushed into events as one formatted multi-line string), and `pendingChoice` (`{ sourceId, prompt, options: [{ label, commands }], continuations: Command[][] } | null` — a presented `choice` awaiting resolution; the prompt and numbered labels are pushed as events at presentation). While `pendingChoice` is non-null the sim accepts ONLY `{ type: "choose", index }` (action words `choose1..choose9`, alias `o1..o9`): out-of-range chooses are rejected naming the valid range, everything else is rejected pointing at the options, and battles can't start (movement is blocked). A valid choose clears `pendingChoice`, runs the chosen option's commands, then resumes the suspended continuations innermost-first — nested choices restack. `snapshot()` (state + rng + seed) includes battle state, vars, passages, and pendingChoice, and round-trips through JSON; `Sim.fromSnapshot(game, snapshot)` restores everything, mid-battle and mid-choice included, defaulting fields missing from older snapshots. World overlays (djt.3): `state.entityOverrides` (moved/removed placed entities), `state.spawnedEntities`, `state.tileOverrides` — EVERY read (entityAt/tileAt/walkability/line-of-sight/interact/observers, via `entitiesOn(mapId)` with effective positions + variant appearance) consults them. Map triggers: `turn` fires because time passed rather than because the player arrived — once at the END of any action that actually advanced the world (a move that moved, an interact that ran an interaction, a choose that resolved one), for triggers on the map the player is standing on then; NOT for rejected actions, battle actions, during a battle, or while a choice is still pending (the beat that opens a choice ticks when it resolves, so one dialogue beat is one turn). Pair `once: false` with `add_var`/`set_var` and `when` for action economies, ambient motion and timed pressure — and put the tick and its reaction in ONE command list, because command-level `when` is evaluated as each command runs while trigger-level `when` is gated for all matching triggers before any of them runs (a separate trigger reading a counter another bumps lags a turn). `enter` fires on arrival (game start for the start map — its events sit in `lastEvents` before the first act — plus portal and `teleport_player` arrivals; NOT respawn), `step` fires on landing on a listed tile (portal landings count); `once` tracking in `state.firedTriggers` ("mapId:id"); a failing `when` skips WITHOUT marking fired; a battle engaging on the same move wins and the trigger stays unfired; trigger commands run through execFrames (frames are `{ sourceId, commands }` — trigger frames speak narrator-voiced: bare `say` text; `pendingChoice.continuationSources` keeps per-frame attribution across saves), and a trigger firing while commands are pending (teleport mid-list, or mid-choice) queues after ALL pending work. Renderer cues: cutscene commands append structured records to `state.lastCues` (cleared each act); sim state lands in the final post-sequence configuration. Endings: `state.ending = { id, text } | null`; any ending refuses further actions ("The game has ended." — `won` keeps its own message); `won` is true iff `ending.id === "victory"`. Variants: `state.variantOverrides` (entityId → forced variantId; beats when-evaluation until cleared; stale ids fall back gracefully).
  - `observe.ts` / `battleObserve.ts` — AI-facing text renderers; `observe(sim)` switches to `describeBattle` (with inventory-aware action list) while a battle is active; undefeated trainers are tagged in the Nearby list. Vars print as a `Vars:` line; multi-line passage events print in full (every line indented), never truncated; party lines are omitted when there is no party (catalog-free games), money always prints. While a choice is pending, `describe` shows `Choice: <prompt>` with the numbered options and the actions line becomes `Actions: choose1..chooseN`. Grid, nearby list, and dialogue speaker names all use EFFECTIVE entities (overlays + variants); a non-victory ending shows `Status: ENDED — <id>`.
  - `language.ts` — `applyLanguage(game, overlay)`: one game, many scripts. STRUCTURE (maps, entities, triggers, flags, choices, endings) is never duplicated; a `games/<id>/lang.<code>.json` overlay carries only words — `{ name, description?, voice?, strings, patches }`. `strings` is keyed by the ORIGINAL text (gettext's msgid trick, so an overlay survives reordering/renaming and only breaks when the source wording itself changes); multi-line passages key on `lines.join("\n")` and may be replaced by a string or an array (a retelling rarely wants the same line count). `patches` (`{path, value}`) handle the rare non-text change and run BEFORE the string pass, so anything spliced in is still translated. Pure: deep-clones, never mutates the source, and returns `{ game, unused, missing }` — the two reports that keep a translation honest as the source drifts. Uncovered strings stay in the original words rather than blanking. An overlaid game must still pass `validateGame`.
  - `save.ts` — pure save-file codec: `makeSaveFile(sim)` / `loadSaveFile(game, data)` wrap snapshots in `{ gameId, gameVersion, snapshot }`; wrong gameId errors actionably, version mismatch warns but loads.
- `packages/play` — AI-facing interfaces: CLI with interactive + `--actions` replay modes (battle and `choose` actions supported; `save [slot]`/`load [slot]` in the REPL, `--from <slot>` to resume a replay; saves live in `<gameDir>/saves/<slot>.json`, gitignored, default slot `quick`), MCP server (`observe`/`act`/`reset`/`save_game`/`load_game`/`validate_game`). The playtest explorer resolves a pending choice deterministically: first option, and after 3 identical presentations of the same choice (same prompt/options/flags/vars) it tries the next option; a fully exhausted identical loop stops the run as `stalled`. Script and explore reports carry `ending: { id, text } | null` and stop with `stopReason: "ended"` on non-victory endings (`win` unchanged in meaning).
- `apps/web` — human-facing Vite app (emoji grid, arrow keys). **Input** (`src/ui/controls.ts`): touch (on-screen d-pad + OK/menu, shown only on coarse pointers and hidden the moment a gamepad appears) and gamepad (polled each rAF frame — pads emit no events) both SYNTHESIZE the same KeyboardEvents the keyboard sends and dispatch them on `window`, so all three feed main.ts's one modal cascade instead of three drifting copies. Synthetic events MUST set `code` as well as `key`: main.ts matches `ev.key` but OverworldView's movement matches `ev.code`. Directions are held-key (keydown/keyup) with a 120ms minimum hold, because the walker only steps when it sees a direction held across a frame — a same-frame tap would otherwise do nothing. **Layout**: the stage is a fixed 768x576 design surface whose overlays are positioned in those coordinates, so the whole surface is `transform: scale(--stage-scale)` (computed in main.ts from the viewport, clamped to <= 1) with `#stage-fit` reserving the scaled box; below 1:1 `image-rendering` switches to `auto` since nearest-neighbour shimmers at fractional scales. text-mode battle panel (1-4 moves, 5-9 items 1-5, Shift+1..6 switch, C catch, X run); imports engine source directly. **Read-aloud** (`src/audio/speech.ts`, key V, Shift+V cycles speed, persisted in localStorage, off by default) narrates dialogue, passages, the choice menu, the title screen and endings over the Web Speech API, so a player who can't read yet can play: the message box and passage pane hand the `Narrator` a `done` callback and take their pacing from the voice instead of a timer (passages turn their own pages), the choice menu speaks the numbered options and re-reads the highlighted one as the caret moves, and stage directions ("You move north.", music/camera cues) are filtered out by `shouldSpeak` — which fails open, so new engine events are spoken rather than silently dropped. Invariant: a caller waiting on the narrator is ALWAYS released (superseded utterance, engine error, or a watchdog for engines that never fire `end`) — a stranded waiter is a frozen game. **Two backends, local first**: (1) a Piper neural voice served at `/__tts` by `piper-plugin.ts`, which spawns `apps/web/tools/piper-server.py` (voice loaded once, ~130ms for a three-second line, LRU-cached, `?voice=` switches lazily among every `.onnx` under `~/.local/share/piper-voices` and `/usr/share/piper-voices`); (2) the browser's Web Speech API. The local backend exists because Web Speech is NOT dependable on Linux — Chromium-family browsers delegate to speech-dispatcher and de-Googled builds (Brave) expose zero voices and answer `speak()` with `synthesis-failed` — and it is also offline and sends no game text anywhere. Hence `hasVoice`/`voiceHint()` separate from `available`: "the API exists" is not "something can be heard", and that failure is surfaced on the chip, in the pause panel and on screen rather than failing silently. Dev-server only; a static build falls back to Web Speech (or run the Python script yourself).
- `games/<id>/game.json` — game content (catalog embedded); a game is a directory of data. Optional `lang.<code>.json` siblings are language overlays (see `language.ts`); the web app discovers them, offers a "Words:" row on the title screen, applies the chosen one via `?lang=<code>`, re-validates the result, and falls back to the game's own words on any problem. `games/trial-of-job/lang.simple.json` is a retelling for a young listener, generated by `tools/build-lang-simple.mjs` — note its HONESTY RULE: a paraphrase must never carry a chapter-and-verse citation, so those become "from the story of Job".
- `docs/design/emberwood.md` — design bible for the full game content

## Conventions & Patterns

- The sim is deterministic with no wall-clock or RNG; a playthrough is a replayable action list — through battles. Keep it that way — tests depend on it.
- Validation errors must name the fix, not just the failure (see `validateGame`).
- Engine stays renderer-agnostic and Node/browser-portable: no `node:` imports in `packages/engine/src`.
- New game mechanics = new zod-schema'd data (commands, interactions), not arbitrary code in game files.
- Action words are 1-based (`move1`, `switch2`, `item3`); `Action`/`PlayerAction` indexes are 0-based.
- Schema changes must be strictly additive and backward compatible: `games/demo` and `games/emberwood` must keep validating with zero errors AND zero warnings (pinned by tests), and `Sim.fromSnapshot` must tolerate older snapshots by defaulting new state fields (`??=`).
